## Design Context

### Users
Self-hosted operators who own a Lingjing subscription and want to turn it into a dependable local API service. Their core jobs are importing a browser session, confirming subscription balance, creating a downstream API key, and copying a working Base URL into tools such as Dify.

### Brand Personality
Trustworthy, utilitarian, and calm. The interface should feel like an operator console: concise, explicit about security boundaries, and confident without marketing language.

### Aesthetic Direction
Preserve the existing compact dark/light console system: IBM Plex typography, cool ink neutrals, one restrained cyan accent, small radii, clear tables, and strong focus states. Prefer hierarchy and readable status information over decoration. Avoid visual rebranding, gradients, glass effects, and generic card grids.

### Implementation Defaults
- Existing stack: React 19, Vite 7, TypeScript, and hand-authored CSS tokens.
- Preserve the current custom component and form patterns; there is no Tailwind, shadcn, headless component library, form library, table library, or virtualization library.
- Use native semantic controls and the existing API/state architecture.
- Extend the existing responsive breakpoints and browser-test harness rather than introducing new dependencies.

### Design Principles
1. Keep one obvious primary action per page and make secondary actions quiet.
2. Show balance, membership, key status, and validation results as operational facts, not decoration.
3. Be honest about security: opening Lingjing cannot import cookies automatically, and secrets shown once must say so plainly.
4. Preserve the established spacing, typography, color, and radius tokens; add no parallel design system.
5. Keep every core action usable without horizontal overflow at both desktop and 390 px mobile widths.
